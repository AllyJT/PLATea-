ohh, the cut in line did badly, it make the error rate go way higher

Found why: when RISK_WAIT_TIMEOUT fired, I released the semaphore slot
right away (in a finally block) even though the abandoned job was still
running in the pool's one worker process. That let a NEW request grab the
freed slot and queue up behind the same still-busy worker -- so more jobs
piled into the one-worker pool than RISK_SLOTS was supposed to allow, and
the worker wasted cycles finishing jobs whose clients had already been
told 503 and walked away. That's why work_score cratered and error_rate
went up instead of down.

Fix: release the slot from a done_callback on the executor future itself,
so it only frees once the job truly finishes (or is cancelled before it
even started) -- not when the client gives up waiting. Note: cancel() only
actually works if the job hasn't started running yet; if it's the one
currently executing, RISK_WAIT_TIMEOUT won't cut it off early, it'll just
keep running to completion. So it bounds queue wait, not total latency in
every case
